Entornos virtuales: qué son y por qué existen

Una carpeta, no un hechizo.

⭐ Lo esencial
  • Un entorno virtual es una carpeta (normalmente .venv) dentro de tu proyecto, con su propio Python y sus propias librerías.
  • Existe para que cada proyecto tenga las versiones que necesita, sin molestar a los demás ni al sistema.
  • No es magia: «activarlo» solo cambia qué python encuentra primero tu terminal.

1. El problema: una sola caja para todos

Cuando instalas Python en tu ordenador, tienes un Python con una carpeta de librerías. Todo lo que instalas con pip install va a esa carpeta común. Mientras solo tienes un programa, no pasa nada. El problema llega con el segundo.

Imagina el Proyecto A, escrito hace un año, que funciona con la versión 2.19 de una librería llamada requests, y el Proyecto B, nuevo, que necesita la 2.34. En una caja compartida solo cabe una versión de cada librería: instalar la nueva pisa a la antigua, y el Proyecto A deja de funcionar.

Y no es solo cuestión de librerías

  • Versiones de librerías: lo que acabas de ver.
  • Versión de Python: un proyecto puede necesitar Python 3.11 y otro, 3.13.
  • El propio sistema: muchas herramientas de tu sistema operativo están escritas en Python y usan ese Python. Si les cambias las librerías, pueden dejar de funcionar. Por eso, en muchas distribuciones de Linux recientes, pip se niega a instalar fuera de un entorno y muestra el error externally-managed-environment.

2. La solución: una caja por proyecto

Un entorno virtual es justo eso: una caja de herramientas propia para cada proyecto, con su Python y sus librerías. Lo que instalas en la caja del Proyecto A no existe para el Proyecto B, y el Python del sistema queda intacto.

Es como si cada habitación de tu casa tuviera su propia caja de herramientas, en lugar de una caja comunitaria donde todo se mezcla y se pierde.

La palabra «virtual» asusta, pero aquí no hay máquinas virtuales ni nada raro. A continuación vas a ver, literalmente, qué es.

3. Quitarle la magia: ¿qué hay dentro?

La forma más rápida de entenderlo es crear uno y mirar dentro. Python trae un comando para crearlo (python3 -m venv) y la costumbre es llamar a la carpeta .venv.

🧪 Pruébalo tú Abre una terminal en una carpeta vacía (en VS Code: Terminal → Nueva terminal) y ejecuta esto. Tus rutas y versiones serán distintas, no importa. 
$ python3 -m venv .venv
$ ls -a
.  ..  .venv
$ ls .venv
bin  include  lib  lib64  pyvenv.cfg
$ ls -l .venv/bin
# (sin los detalles que no importan)
activate  activate.csh  activate.fish  Activate.ps1
pip  pip3  pip3.13
python -> python3
python3 -> /usr/local/bin/python3
python3.13 -> python3
$ cat .venv/pyvenv.cfg
home = /usr/local/bin
include-system-site-packages = false
version = 3.13.18
executable = /usr/local/bin/python3.13
command = /usr/local/bin/python3 -m venv /home/ana/mi-proyecto/.venv

Eso es un entorno virtual. Una carpeta con tres cosas que importan:

  • Tu código no está ahí. El entorno solo contiene Python y librerías. Tus archivos .py viven en tu proyecto, fuera de .venv.
  • Ocupa poco al principio: unos 13 MB recién creado, y casi todo es pip.
  • El nombre .venv es una costumbre. Pero muy extendida: VS Code y uv lo buscan con ese nombre. El punto inicial lo oculta en muchas listas de archivos.
💡 En Windows La carpeta se llama Scripts en lugar de bin, el comando para crear el entorno suele ser python -m venv .venv y se activa con .venv\Scripts\activate. La idea es la misma.

4. ¿Y qué hace «activar»?

Aquí está la parte que parece magia. Cuando escribes python3 en una terminal, ella no sabe dónde está ese programa: lo busca en una lista de carpetas, en orden, y ejecuta el primero que encuentra. Esa lista se llama PATH.

🧪 Pruébalo tú Mira qué python3 usa tu terminal antes y después de activar: 
$ which python3
/usr/local/bin/python3
$ source .venv/bin/activate
(.venv) $ which python
/home/ana/mi-proyecto/.venv/bin/python
(.venv) $ python -c "import sys; print(sys.prefix)"
/home/ana/mi-proyecto/.venv
(.venv) $ echo $VIRTUAL_ENV
/home/ana/mi-proyecto/.venv
(.venv) $ deactivate
$ which python3
/usr/local/bin/python3

Eso es todo lo que hace activate: pone la carpeta .venv/bin la primera de la lista, define la variable VIRTUAL_ENV y cambia el indicador de tu terminal para que veas (.venv). deactivate lo deshace. No instala nada, no copia nada y no «entra» en ningún sitio.

💡 No hace falta activar Si escribes la ruta completa, el entorno funciona igual, sin activar nada. De hecho, el programa pip que está dentro del entorno lleva escrita, en su primera línea, la ruta del Python al que pertenece: 
$ head -1 .venv/bin/pip
#!/home/ana/mi-proyecto/.venv/bin/python3
$ .venv/bin/python -c "import requests; print(requests.__version__)"
2.34.2
Más adelante verás que VS Code y uv hacen todo esto por ti.

5. Instalar librerías dentro

Con el entorno activado, lo que instales con pip cae en site-packages de ese entorno y en ningún otro sitio:

🧪 Pruébalo tú 
(.venv) $ pip list
Package Version
------- -------
pip     26.2.2
(.venv) $ pip install requests
(.venv) $ pip list
Package            Version
------------------ ----------
certifi            2026.10.23
charset-normalizer 3.5.2
idna               3.20
pip                26.2.2
requests           2.34.2
urllib3            2.8.0
(.venv) $ ls .venv/lib/python3.13/site-packages
certifi  charset_normalizer  idna  pip  requests  urllib3  (y las carpetas .dist-info)

Fíjate en que pediste requests y llegaron seis paquetes: requests necesita otras librerías para funcionar y pip las trae todas. Esas «librerías de tus librerías» se llaman dependencias, y son una de las razones por las que conviene que alguien (uv) lleve la cuenta de ellas.

Y si algo sale mal, no pasa nada: se borra la carpeta y se crea otra vez.

$ rm -rf .venv
$ ls -a
.  ..

Tu código sigue intacto, porque nunca estuvo ahí dentro.

⚠️ Ojo: no lo copies a otro sitio No copies la carpeta .venv a otro ordenador ni a otra carpeta. Dentro hay rutas absolutas (como la primera línea de pip) y enlaces a un Python concreto de esta máquina. Un entorno se vuelve a crear en cada sitio; en el paso 4 verás cómo hacerlo con un solo comando. Por la misma razón, .venv no se sube a Git.

❓ Compruébalo

Si borro la carpeta .venv, ¿pierdo mi código?

No. El entorno solo contiene Python y librerías. Tu código vive fuera, en tu proyecto. Lo único que pierdes es lo instalado dentro, que se puede volver a instalar.

¿Qué hace exactamente source .venv/bin/activate?

Pone la carpeta .venv/bin la primera en el PATH, define VIRTUAL_ENV y cambia el indicador de la terminal a (.venv). Nada más. Por eso python pasa a ser el del entorno, y por eso deactivate lo deshace todo.

¿Puedo copiar .venv a otro ordenador para ahorrarme instalar?

No. Contiene rutas absolutas y enlaces a un Python concreto de tu máquina, así que en otro ordenador no funcionaría. Se vuelve a crear allí a partir de la lista de librerías del proyecto, algo que veremos en el paso 4.
