Librerías y versiones: uv y pyproject.toml

Cómo hacer que tu proyecto funcione igual en cualquier ordenador.

⭐ Lo esencial
  • Las librerías cambian de versión con el tiempo. Un pip install requests de hoy no es el de dentro de un año.
  • pyproject.toml dice qué librerías necesitas. uv.lock apunta exactamente qué versiones se instalaron.
  • Con esos dos archivos, otra persona (o tú en otro ordenador) recrea el mismo entorno con un solo comando: uv sync.

1. El problema de siempre: «en mi ordenador funciona»

Imagina que haces un programa que usa requests. Lo instalas con pip install requests y funciona. Se lo pasas a un compañero, o lo abres en otro ordenador seis meses después.

  • Tu compañero escribe pip install requests y recibe la versión de ese día, que puede ser otra.
  • Además, requests trae sus propias dependencias (viste seis paquetes en el paso 1), y cada una puede haber cambiado también.
  • Ni siquiera sabe que necesita requests, si no se lo has apuntado en algún sitio.

Cualquier cambio de versión puede romper algo, y encontrar cuál es lo más tedioso. La solución es doble: anotar qué necesitas y anotar qué versiones exactas funcionaron.

3. Verlo funcionar

Partimos de un proyecto recién creado, con uv. Añadimos requests:

🧪 Pruébalo tú 
$ uv add requests
Resolved 13 packages in 1.00s
Prepared 6 packages in 426ms
Installed 6 packages in 4ms
 + certifi==2026.10.23
 + charset-normalizer==3.5.2
 + idna==3.20
 + requests==2.34.2
 + urllib3==2.8.0
Esa única orden hizo tres cosas: apuntó requests en pyproject.toml, anotó las versiones exactas en uv.lock e instaló todo en .venv.

Con uv tree ves cómo se relacionan las librerías (cuáles necesitan a cuáles):

$ uv tree
mi-proyecto v0.1.0
├── requests v2.34.2
│   ├── certifi v2026.10.23
│   ├── charset-normalizer v3.5.2
│   ├── idna v3.20
│   └── urllib3 v2.8.0
├── pytest v9.2.0 (group: dev)
│   ├── iniconfig v2.3.1
│   ├── packaging v26.3
│   ├── pluggy v1.7.0
│   └── pygments v2.21.0
└── ruff v0.17.3 (group: dev)

Las que dicen (group: dev) son herramientas de desarrollo (pruebas, estilo). Tu programa no las necesita para funcionar; las usas tú mientras lo escribes.

4. Llevarlo a otro ordenador

Aquí está la gracia. En otro equipo (que tenga uv y Git) solo hay que traer el proyecto y sincronizar:

🧪 Pruébalo tú 
$ git clone https://github.com/tu-usuario/mi-proyecto
$ cd mi-proyecto
$ uv sync
Using CPython 3.13.18 interpreter at: /usr/local/bin/python3.13
Creating virtual environment at: .venv
Resolved 13 packages in 1ms
Installed 12 packages in 8ms
 + certifi==2026.10.23
 + charset-normalizer==3.5.2
 + idna==3.20
 + iniconfig==2.3.1
 + mi-proyecto==0.1.0 (from file:///…/mi-proyecto)
 + packaging==26.3
 + pluggy==1.7.0
 + pygments==2.21.0
 + pytest==9.2.0
 + requests==2.34.2
 + ruff==0.17.3
 + urllib3==2.8.0
Mismas versiones que en el ordenador original, hasta el último decimal. No instaló lo más reciente: instaló lo que decía el uv.lock.

Por eso no hace falta copiar .venv (ya viste en el paso 1 que no se puede): se vuelve a construir en segundos, porque uv guarda las librerías descargadas en una caché y las enlaza en lugar de descargarlas otra vez.

💡 ¿Y requirements.txt y pip freeze? Es la forma clásica de hacer algo parecido: pip freeze > requirements.txt guarda las versiones instaladas y pip install -r requirements.txt las recupera. Funciona, pero lo apuntas a mano, mezcla lo que pediste con lo que vino de rebote y no distingue las herramientas de desarrollo. uv lleva esa cuenta él solo.

❓ Compruébalo

Si borro .venv por error, ¿pierdo las librerías?

No. Ejecuta uv sync y se reconstruye igual, porque la receta (pyproject.toml y uv.lock) sigue ahí.

¿Qué pasa si edito pyproject.toml a mano y añado una librería?

La próxima vez que ejecutes uv run o uv sync, uv actualiza el uv.lock y el entorno. Pero lo más cómodo es usar uv add, que lo hace todo de golpe.

¿Y si quiero actualizar una librería a su última versión?

Con uv lock --upgrade-package requests pides que se busque una versión nueva de esa librería y se anote en el uv.lock. Después, uv sync la instala.
