El día a día: pruebas, Ruff y Claude

Cómo se trabaja una vez montado el proyecto.

⭐ Lo esencial
  • El código va en src/ y las pruebas en tests/. Cada función nueva nace con su prueba.
  • El ciclo es: prueba que falla → código mínimo → prueba que pasa → commit.
  • Claude sigue las reglas del archivo CLAUDE.md y dos procedimientos del proyecto. Ruff revisa cada archivo que edita. Tú pides cosas con normalidad.

2. El ciclo de trabajo: primero la prueba

Una prueba es una función que comprueba que otra hace lo que debe. La idea (se llama TDD, desarrollo guiado por pruebas) es escribirla antes del código. Suena al revés, pero obliga a pensar qué quieres antes de cómo lo harás, y te deja con una red de seguridad: si más tarde algo rompe lo que ya funcionaba, la prueba lo cuenta.

Un ejemplo real, paso a paso

Queremos una función que calcule el IVA. Rojo: escribimos la prueba antes que la función.

# tests/test_impuestos.py
from mi_proyecto.impuestos import calcular_iva


def test_iva_general_del_21_por_ciento():
    assert calcular_iva(100) == 21

$ uv run pytest
...
E   ModuleNotFoundError: No module named 'mi_proyecto.impuestos'
1 error in 0.09s

Falla, y por la razón correcta: el módulo todavía no existe. Verde: escribimos lo mínimo.

# src/mi_proyecto/impuestos.py
def calcular_iva(precio: float, tipo: float = 0.21) -> float:
    return round(precio * tipo, 2)

$ uv run pytest
tests/test_impuestos.py .                                   [ 50%]
tests/test_main.py .                                        [100%]
2 passed in 0.02s

Guardar: un commit con una frase clara. Ya lo sabes hacer (paso 7).

$ git add -A
$ git commit -m "feat(impuestos): add VAT calculation"
🧪 Pruébalo tú: míralo en la vista Testing
  1. Abre el matraz de la barra lateral (paso 2). Verás test_main.py y test_impuestos.py.
  2. Cambia en tu prueba el 21 por 22 y pulsa el triángulo: aparece ✘ y la diferencia entre lo esperado y lo obtenido.
  3. Haz clic derecho sobre la prueba y elige Debug Test: se detiene en un punto y puedes ver las variables.
  4. Devuélvelo a 21.

3. Ruff trabaja solo

Además de formatear al guardar (paso 2), en este proyecto Ruff se ejecuta cada vez que Claude edita un archivo Python. Es un «gancho» del proyecto (hook): una orden que se dispara tras cada edición. Si queda algo que Ruff no sabe arreglar, se lo devuelve a Claude para que lo corrija. Así es como se ve un aviso real:

$ uv run ruff check
F401 [*] `os` imported but unused
 --> src/mi_proyecto/malo.py:1:8
  |
1 | import os
  |        ^^
I001 [*] Import block is un-sorted or un-formatted

Y esto es lo que cambiaría el formateador (uv run ruff format --diff) en una función mal escrita:

-def f( x ):
-    return x+1
+
+def f(x):
+    return x + 1

Los marcados con [*] se arreglan solos con uv run ruff check --fix.

4. Cómo trabaja Claude en tu proyecto

Cuando abres el proyecto y le pides algo a Claude, él lee un archivo llamado CLAUDE.md: las reglas de la casa. Además hay dos procedimientos que aplica según lo que le pidas, un gancho y una lista de permisos.

Cuando pides…Claude sigue…Y hace…
Código nuevo o un arreglopy-tareaDiseña en el chat → escribe una prueba que falla → escribe el código → comprueba pruebas y Ruff → commit → apunta en el diario → te cuenta qué hizo.
Refactorizar o limpiarpy-refactorExplica qué mejoraría → comprueba que hay pruebas (si no, las escribe primero) → te deja elegir entre modo automático o interactivo → trabaja en pasos pequeños con un commit por cada uno.
Instalar una libreríaCLAUDE.mdTe pregunta antes de ejecutar uv add.
Subir a GitHubCLAUDE.mdSolo hace git push si se lo pides o si lo autorizaste al crear el proyecto.
💡 El diario de trabajo Claude apunta cada trabajo importante en .claude/dev-journal.md: fecha, qué se hizo, decisiones y próximos pasos. Es tu cuaderno de bitácora y el suyo: si una conversación se corta, Claude lo lee para retomar el hilo. No se sube a Git, porque son notas personales.

Una conversación típica

🧪 Pruébalo tú Abre el panel de Claude Code en tu proyecto y escribe:

Observa cómo, sin que se lo pidas: te cuenta el diseño en unas líneas, escribe la prueba, la ve fallar, escribe el código, la ve pasar y hace el commit con un mensaje del tipo feat(impuestos): add VAT calculation. Después prueba con «refactoriza la función» y verás cómo te pregunta si prefieres modo automático o interactivo.
⚠️ Ojo: Claude también se equivoca Las pruebas y Ruff son tu seguro, pero revisa lo que hace: lee el commit (git show), entiende la función que escribió y mira que la prueba compruebe lo que de verdad te importa. Una prueba que siempre pasa no protege nada.

❓ Compruébalo

¿Y si mi proyecto ya tiene código y no tiene pruebas?

Pídele a Claude que refactorice: antes de tocar nada, py-refactor comprueba si hay pruebas y, si no, ofrece escribir primero unas que fijen cómo se comporta el código ahora.

¿Puedo cambiar las reglas de Claude?

Sí. CLAUDE.md y los procedimientos de .claude/skills/ son texto. Cambia lo que quieras (por ejemplo, el idioma de los comentarios) y Claude lo seguirá desde la siguiente sesión.

¿Por qué el diario y los permisos están dentro de .claude/?

Porque es la carpeta donde Claude Code guarda lo suyo. Los permisos (settings.json) sí se suben a Git, para que quien clone el proyecto tenga las mismas reglas; el diario (dev-journal.md) no.
